# Способы выразить архитектурно-специфичные действия: intrinsic, inline asm, отдельный .S

Окружение: gcc 14.3, AMD Ryzen 5 4600H (Zen 2: есть popcnt/avx2/bmi2, нет avx512), Linux x86-64 (WSL2).
Запуск всего: `./run.sh`.

## 1. Какие вообще есть способы

От самого переносимого к самому низкоуровневому:

| # | Способ | Кто отвечает за выбор инструкции | Видимость для оптимизатора |
|---|---|---|---|
| 0 | **Переносимая идиома** (`(x<<n)\|(x>>(64-n))`) | компилятор распознаёт шаблон | полная |
| 1 | **Стандартная библиотека**: C23 `<stdbit.h>`, C++20 `<bit>` (`std::popcount`, `std::rotl`) | компилятор | полная |
| 2 | **Builtin компилятора**: `__builtin_popcountll`, `__builtin_clz`, `__builtin_add_overflow` | компилятор | полная |
| 3 | **Intrinsic**: `_mm_popcnt_u64`, `_mm256_add_epi32`, `__builtin_ia32_*` | программист выбирает инструкцию, компилятор — регистры и планирование | почти полная (компилятор знает семантику) |
| 4 | **Inline assembler**: `__asm__("popcnt %1,%0" : "=r"(r) : "rm"(x) : "cc")` | программист пишет инструкцию, компилятор — только распределение регистров по ограничениям | **нулевая**: тело asm для компилятора непрозрачная строка |
| 5 | **Отдельный файл** `.S` / `.s`, вызов по ABI | программист пишет всё, включая пролог и соблюдение ABI | нулевая, плюс **нельзя встроить** |
| 6 | Отдельная единица трансляции на C с `#ifdef` по архитектуре | компилятор | полная внутри файла, межмодульно только с LTO |

Способы 0–2 архитектурно-специфичны только по результату: исходник переносим, инструкцию подставляет компилятор. Способы 3–5 специфичны по исходнику.

## 2. Бенчмарк: одна операция, все способы

`popcnt_bench.c` + `popcnt_asm.S`. Задача: сумма popcount по массиву 32768 слов (256 КБ, помещается в L2), 3000 повторов, **best-of-5**.

Best-of-5 здесь обязателен: при одиночных прогонах на этой машине разброс достигал 2–3 раз (троттлинг ноутбука). Ранние одиночные замеры давали ложный порядок среди быстрых вариантов.

```
способ                                 лучшее,с   худшее  Гслов/с  сумма
C: цикл Кернигана (переносимо)            2.401    2.650     0.04   OK   x1
C: SWAR-трюк (переносимо)                 0.124    0.134     0.79   OK   x19
__builtin_popcountll, без -mpopcnt        0.177    0.227     0.56   OK   x14
__builtin_popcountll + target("popcnt")   0.041    0.044     2.38   OK   x58
C23 stdc_count_ones + target("popcnt")    0.039    0.053     2.50   OK   x61
intrinsic _mm_popcnt_u64                  0.038    0.043     2.57   OK   x63
inline asm "popcnt" на слово              0.041    0.046     2.37   OK   x58
.S: вызов popcnt1() на каждое слово       0.133    0.142     0.74   OK   x18
.S: popcnt_words() на весь массив         0.040    0.049     2.47   OK   x60
.S: popcnt_words_xor() (xor перед popcnt) 0.049    0.068     2.03   OK   x49
```

Что из этого следует:

1. **Все способы, порождающие инструкцию inline, дают одно и то же: 0.038–0.041 с.** Intrinsic, builtin, C23-функция и inline asm неразличимы. Разница между ними внутри шума.
2. **Главный выигрыш даёт не способ записи, а разрешение инструкции.** `__builtin_popcountll` без `-mpopcnt`/`target` компилируется в вызов `__popcountdi2` из libgcc и работает 0.177 с, то есть медленнее ручного SWAR-трюка. С `target("popcnt")` — 0.041 с, в 4.3 раза быстрее. Флаг компиляции важнее выбора между intrinsic и asm.
3. **Отдельный .S проигрывает на мелкой гранулярности: 0.133 с против 0.038, в 3.5 раза.** Причина не в качестве кода (там одна инструкция `popcnt` и `ret`), а в том, что **вызов нельзя встроить**: на каждое слово идёт `call`/`ret` плюс ограничения ABI на регистры. Проверил с `-flto`: не помогает, к моменту линковки это уже объектный код, а не IR.
4. **Тот же .S на крупной гранулярности (цикл целиком) полностью догоняет: 0.040 с.** Вывод: отдельный ассемблерный файл окупается только тогда, когда за один вызов делается много работы.
5. **Ручная «оптимизация» оказалась вредной.** Я добавил `xor %edx,%edx` перед `popcnt`, чтобы разорвать ложную зависимость по регистру-приёмнику. На Intel Sandy Bridge–Ice Lake это ускоряет, но на Zen 2 ложной зависимости нет, и лишний `xor` дал замедление: 0.049 против 0.040. Это типичная проблема ручного ассемблера: оптимизация под один микроархитектурный профиль вредит на другом, а компилятор с `-march=native` подстроился бы сам.

### Во что это компилируется

Intrinsic (`p_intrinsic`), gcc -O2:
```asm
.L31:   xorl    %edx, %edx
        addq    $8, %rdi
        popcntq -8(%rdi), %rdx      ; компилятор сам вставил xor против ложной зависимости
        addq    %rdx, %rax
        cmpq    %rdi, %rcx
        jne     .L31
```

Inline asm (`p_inline_asm`), gcc -O2:
```asm
.L20:   #APP
        popcnt (%rdi), %rdx          ; компилятор не заглядывает внутрь
        #NO_APP
        addq    $8, %rdi
        addq    %rdx, %rax
        cmpq    %rcx, %rdi
        jne     .L20
```

Видно главное различие: для intrinsic компилятор **понимает семантику** и сам добавил `xorl %edx,%edx`, зная про особенность `popcnt`. Для inline asm он этого сделать не может, тело для него — строка.

## 3. Чем inline asm опасен: `pitfalls.c`

Три ошибки, которые не видны на `-O0` и проявляются на `-O2`.

### 3.1 Не описали побочный эффект — запись потерялась

```c
int x=0; __asm__ volatile("movl $42, (%0)" :: "r"(&x));   // компилятор не знает про запись в x
return x;
```
```
gcc -O0:  bad_store()  = 42   (ждём 42)
gcc -O2:  bad_store()  = 0    <-- НЕВЕРНО
```
На `-O2` компилятор видит `x=0`, не видит присваиваний и подставляет константу 0. Инструкция в выводе есть, но результат не читается:
```asm
bad_store:
        leaq    4(%rsp), %rax
        #APP
        movl $42, (%rax)          ; запись выполняется...
        #NO_APP
        xorl    %eax, %eax        ; ...но возвращается 0
```
Правильно: операнд вывода `"=m"(x)` либо clobber `"memory"`. Вариант `good_store` даёт 42 на обоих уровнях.

Это ровно тот класс ошибок, который делает inline asm опасным: **работает на отладочной сборке и ломается на релизной**.

### 3.2 Компилятор не может свернуть константу через asm

```c
__builtin_popcountll(0xFF00FFull)   ->   movl $16, %eax        ; посчитано на этапе компиляции
inline asm popcnt на той же константе ->  movl $16711935, %eax
                                          popcnt %rax,%rax     ; считается во время выполнения
```
То же касается устранения общих подвыражений, выноса из цикла и векторизации: всё это через inline asm не проходит. Intrinsic такой барьер не ставит.

### 3.3 Early-clobber

```c
__asm__("mov %1,%0\n\tadd %2,%0" : "=r"(out) : "r"(a),"r"(b));    // без "&"
```
Компилятор вправе назначить `out` тот же регистр, что и `b`, и тогда первый `mov` затрёт вход. На моих прогонах gcc распределил регистры удачно и оба варианта дали 7, то есть **ошибка не воспроизвелась**. Это и есть худший сценарий: код неверен, но тест зелёный, а сломается при другой версии компилятора или другом окружающем коде. Правильно `"=&r"`.

## 4. Переносимость: `portable.c`

Одна операция `rotl` тремя способами даёт одинаковый результат `0x68ACF13579BDE024`, но переносимость разная:

| Способ | Компилируется на | Результат на x86-64 |
|---|---|---|
| `(x<<n) \| (x>>(64-n))` | любая архитектура, любой компилятор | **одна инструкция `rolq`** (проверил в выводе `-S`) |
| `_lrotl(x,n)` | только x86 | `rolq` |
| `__asm__("rolq %%cl,%0"...)` | только x86 **и** только gcc/clang (MSVC не понимает синтаксис) | `rolq` |

Переносимая идиома дала ту же инструкцию, что и ассемблер. Это общее правило для распространённых операций: rotate, popcount, byteswap, clz/ctz, overflow-checked арифметику современные компиляторы распознают. Писать под них intrinsic или asm смысла нет.

### Диспетчеризация по CPU во время выполнения

Архитектурная специфика — это не только «какая архитектура», но и «какие расширения есть у конкретного экземпляра». Одна сборка, выбор реализации при старте:

```c
__attribute__((target("default")))                  static uint64_t pc_impl(...);
__attribute__((target("popcnt")))                   static uint64_t pc_impl_popcnt(...);
__attribute__((target("avx512vpopcntdq,avx512f")))  static uint64_t pc_impl_avx512(...);
...
__builtin_cpu_init();
pc_t chosen = __builtin_cpu_supports("avx512vpopcntdq") ? pc_impl_avx512
            : __builtin_cpu_supports("popcnt")          ? pc_impl_popcnt : pc_impl;
```
```
popcnt=4  avx2=1024  bmi2=131072  avx512f=0  avx512vpopcntdq=0
выбрана реализация: popcnt
```

Это работает с intrinsic и builtin (атрибут `target` меняет то, что разрешено порождать компилятору), но **не работает с отдельным .S**: там разрешённый набор инструкций определяется на этапе ассемблирования, и нужны отдельные варианты функции с ручным выбором указателя. Для inline asm атрибут `target` тоже не помогает: ассемблер примет любую инструкцию, которую вы написали, независимо от `-march`, и падение произойдёт на чужом CPU во время выполнения.

## 5. Сравнение интерфейсов

| Критерий | Intrinsic | Inline asm | Отдельный .S |
|---|---|---|---|
| Распределение регистров | компилятор | компилятор по вашим ограничениям | **вручную** |
| Соблюдение ABI | не ваша забота | не ваша забота | **вручную**: аргументы, возврат, caller/callee-saved, выравнивание стека, red zone |
| Встраивание | да | да | **нет**, даже с LTO |
| Свёртка констант, CSE, вынос из цикла | да | **нет** | нет |
| Автовекторизация окружающего кода | да | **обычно ломается** | не применимо |
| Планирование инструкций под микроархитектуру | компилятор, по `-march`/`-mtune` | частично | **вручную**, и устаревает |
| Проверка на этапе компиляции | типы, число аргументов | только синтаксис ассемблера | только синтаксис |
| Класс ошибок | обычные ошибки в C | **молчаливые: ограничения, clobbers, early-clobber** | ABI, регистры |
| Переносимость между компиляторами | хорошая (x86-intrinsic поддержаны gcc/clang/MSVC/icc) | **плохая**: MSVC не поддерживает asm на x64 вообще | средняя: свой синтаксис/ассемблер |
| Отладочная информация | обычная | ограниченная | нужна вручную (`.cfi_*`) |
| Диспетчеризация через `target`/`target_clones` | да | нет | нет |
| Доступ к произвольной инструкции | **только к тем, для которых intrinsic есть** | к любой | к любой |
| Контроль над точной последовательностью | нет | частичный | **полный** |

## 6. Что использовать

Порядок выбора: **брать первый подходящий сверху.**

1. **Переносимая идиома или стандартная библиотека** (C23 `<stdbit.h>`, C++20 `<bit>`, `__builtin_*`). Покрывает popcount, clz/ctz, rotate, byteswap, overflow-checked арифметику, атомарные операции, префетч, барьеры. Мой замер: `stdc_count_ones` (0.039 с) не отличается от intrinsic (0.038 с) и от inline asm (0.041 с). Проигрыша нет, а код переносим и полностью прозрачен оптимизатору.
   Обязательное условие: **разрешить инструкцию** через `-march=`, `-mpopcnt` или `__attribute__((target(...)))`. Без этого 0.177 с вместо 0.041, это в 4.3 раза хуже, и никакой ассемблер этого не компенсирует, если остальной код собран без нужного `-march`.

2. **Intrinsic** — когда операции нет в стандарте: SIMD (`_mm256_*`), криптографические расширения (AES-NI, SHA), `_mm_prefetch`, `_mm_pause`, `__rdtsc`, `_xgetbv`. Это основной рабочий инструмент для архитектурно-специфичного кода. Компилятор сохраняет всю оптимизацию вокруг, знает про ложные зависимости (в моём примере сам вставил `xorl`) и поддерживает диспетчеризацию через `target`.

3. **Inline asm** — только когда intrinsic не существует:
   - системные инструкции: `cpuid`, `rdmsr`/`wrmsr`, `lgdt`, `invlpg`, `swapgs`, `sysret`, `hlt`;
   - обращение к конкретному регистру: `%cr3`, `%gs:offset` (per-CPU данные в ядре);
   - системные вызовы напрямую (`syscall`, `int 0x80`), точки входа в обработчики прерываний;
   - трюки со стеком и переключение контекста.
   
   Правила: всегда `volatile` для инструкций с побочными эффектами, всегда перечислять clobbers (`"memory"`, `"cc"`), `"=&r"` там, где приёмник пишется до чтения входов, и **обязательно проверять на `-O2`, а не только на `-O0`** — пункт 3.1 показывает, почему.

4. **Отдельный .S** — когда:
   - **за один вызов делается много работы** и накладные расходы на вызов теряются. В бенчмарке крупная гранулярность дала 0.040 с (наравне с intrinsic), а мелкая 0.133 с (в 3.5 раза хуже);
   - нужен полный контроль над кадром стека и ABI: точка входа ядра, `_start`, обработчик прерывания, переключение контекста, батут для setjmp/longjmp, стартовый код прошивки до настройки стека;
   - нужны директивы, недоступные из C: собственная `.cfi`-разметка, размещение в конкретной секции, выравнивание страниц, self-modifying code и alternatives-патчинг (как `.altinstructions` в ядре Linux);
   - функция должна существовать до того, как доступна среда C.

   Цена: ABI, регистры и разметка отладчика на вас, встраивания не будет никогда, и код придётся поддерживать отдельно для каждой архитектуры.

5. **Отдельная единица трансляции на C с `#ifdef`** — недооценённый вариант. Архитектурная специфика изолируется в одном файле (`arch/x86/…`, `arch/arm64/…`), но внутри остаётся обычный C с intrinsic, доступный оптимизатору. Так устроено ядро Linux и большинство переносимых библиотек. Обычно это лучший способ **организации**, ортогональный выбору между 1–4.

### Короткое правило

> Пишите переносимо, разрешайте инструкции флагами. Не хватает — intrinsic. Нет intrinsic — inline asm с полными ограничениями. Нужен контроль над ABI или очень крупный блок работы — отдельный .S.

Проверенный факт, ради которого всё это измерялось: **на популярных операциях выбор между intrinsic, builtin, стандартной функцией и inline asm не влияет на скорость** (0.038–0.041 с, разница в шуме). Влияют две другие вещи: разрешена ли инструкция компилятору (в 4.3 раза) и можно ли встроить вызов (в 3.5 раза). Поэтому ассемблер ради скорости на мелких операциях — почти всегда лишняя работа и лишний риск.
