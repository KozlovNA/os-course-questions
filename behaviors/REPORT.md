# Виды поведения в C и C++: undefined, implementation-defined, unspecified, defined

Окружение замеров: gcc 14.3, Linux x86-64 (WSL2), 12 ядер. Запуск: `./run.sh`.

## 1. Классификация

| Вид | Что гарантирует стандарт | Пример |
|---|---|---|
| Defined | Результат однозначен везде | `unsigned` переполнение (по модулю 2^n) |
| Implementation-defined | Несколько вариантов, реализация **выбирает и документирует** | `sizeof(long)`, знаковость `char`, `-8 >> 1`, `(int)3000000000u`, endianness |
| Unspecified | Несколько вариантов, **документировать не обязана**; программа корректна | порядок вычисления аргументов функции |
| Undefined (UB) | **Никаких требований** | знаковое переполнение, `*NULL`, выход за массив, нарушение strict aliasing, `1 << 31` для `int` (C++ до C++20) |

## 2. Примеры (файлы)

- `01_behaviors.c`: implementation-defined и unspecified.
  Вывод: `sizeof(long)=8`, `char` знаковый, `-8>>1=-4`, little-endian, `printf("%d %d", k++, k++)` печатает `1 0` (gcc считает справа налево).
- `02_ub_optimizer.c`: как оптимизатор использует UB.
  - `x + 1 > x` при `-O2` даёт `1`, при `-O2 -fwrapv` даёт `0` для `INT_MAX`. В ассемблере остаётся `movl $1, %eax; ret`, сравнения нет.
  - `int v = *p; if (!p) return -1;`: проверка `if(!p)` удалена (`movl (%rdi), %eax; ret`).
    **Оговорка:** при вызове с `&a` вывод равен 5 на любом уровне оптимизации, то есть сам по себе вывод программы ничего не показывает. Удаление проверки видно только в машинном коде. Развёрнуто в разделе 2a.
  - UBSan сообщает `signed integer overflow` и `left shift of 1 by 31 places`.
  - Тест с циклом `for(int i=start; i>=start; i++)` на gcc 14 «бесконечный цикл» **не** воспроизвёл. Это UB, поведение зависит от версии компилятора, полагаться нельзя.

## 2a. Почему «удалённая проверка» опасна, если вывод не меняется

Разбор вопроса: в `nullchk(&a)` указатель валидный, поэтому `5` возвращается всегда. Верно. Опасность не в этом вызове, а в том, что проверка физически исчезает из кода, и её не будет тогда, когда она понадобится.

### `05_nullcheck.c` — с валидным указателем разницы нет, с NULL есть

```
bad(&a)=5  good(&a)=5              <- одинаково, как и должно быть

bad(NULL)  -> SIGSEGV              <- разыменование идёт ДО проверки
good(NULL) -> вернула -1           <- проверка ДО разыменования
```
Здесь `bad` падает и на `-O0`, и на `-O2`: разыменование выполняется в обоих случаях. Разница между уровнями оптимизации тут ещё не видна.

### `06_nullcheck_real.c` — схема CVE-2009-1897 (драйвер tun в ядре Linux)

Опасная ситуация возникает, когда **само разыменование удаляется как мёртвый код, а выведенный из него факт остаётся**:
```c
int handle(struct cfg *s, int *out){
    int lim = s->limit;      // 1) разыменование, значение пока не нужно
    if (!s) { *out = 0; return -1; }   // 2) компилятор удалит: "s не может быть NULL"
    *out = lim * 2;          // 3) сюда попадём с s == NULL
    return 0;
}
```
Машинный код:
```asm
; gcc -O0                          ; gcc -O2
        movl    (%rax), %eax               endbr64
        movl    %eax, -4(%rbp)             movl    (%rdi), %eax
        cmpq    $0, -24(%rbp)   <-- проверка есть      addl    %eax, %eax
        jne     .L2                        movl    %eax, (%rsi)
        ...                                xorl    %eax, %eax
                                           ret       <-- ни cmp, ни ветвления
```
На `-O2` весь путь `if (!s) { *out = 0; return -1; }` исчез. В обычной программе оба варианта падают, потому что нулевая страница не отображена (`vm.mmap_min_addr = 65536`). Но в ядре, на системе без MMU или там, где атакующий может отобразить нулевую страницу, `-O0`-версия штатно вернула бы `-1`, а `-O2`-версия продолжила бы работу с нулевым указателем. Это и есть та уязвимость.

### `07_check_deleted.c` — неверный ответ вообще без падения

Самый наглядный случай: указателей нет, падения нет, просто **неправильный результат**.
```c
int r = x + 100;
if (r < x) return -1;    // "переполнение" — на -O2 удаляется
return r;
```
```
вход x = 2147483597 (INT_MAX - 50), ожидается -1 во всех случаях

                                        gcc -O0        gcc -O2
проверка ПОСЛЕ  (r < x)                  -1            -2147483599   <-- НЕВЕРНО
проверка ДО     (x > INT_MAX-100)        -1            -1
__builtin_add_overflow                   -1            -1
```
Ассемблер объясняет всё:
```asm
; -O0: сравнение на месте        ; -O2: от функции осталось две инструкции
        cmpl    -20(%rbp), %eax          leal    100(%rdi), %eax
        jge     .L2                      ret
```
Программа не падает, UBSan без запуска молчит, тесты на малых значениях проходят. Ошибка проявится только на краю диапазона и только в релизной сборке.

**Вывод:** «проверка удалена» означает не изменение вывода конкретного вызова, а то, что защитного кода больше нет в бинарнике. Проверять нужно **до** потенциально неопределённой операции, а не после неё.

## 2b. Откуда в strict aliasing берётся 1073741824

`08_aliasing_bits.c`. Число не случайное и не «мусор из памяти»: это **битовое представление `2.0f`, прочитанное как `int`**.

```c
int alias(int *i, float *f){
    *i = 1;      // в 4 байта кладём целое 1
    *f = 2.0f;   // в ТЕ ЖЕ 4 байта кладём float 2.0
    return *i;   // читаем обратно как int
}
```

Разбор `2.0f` по IEEE-754 (single precision): `2.0 = 1.0 × 2¹`, значит знак 0, порядок `1 + 127 = 128`, мантисса 0.

```
int   1     =          1 = 0x00000001 = 0 00000000 00000000000000000000001
float 2.0f  = 1073741824 = 0x40000000 = 0 10000000 00000000000000000000000
                                        ^ ^^^^^^^^ ^^^^^^^^^^^^^^^^^^^^^^^
                                      знак  порядок          мантисса
```

`0x40000000` — это ровно `2³⁰ = 1073741824`. Единственный установленный бит — младший бит поля порядка, а он в 32-битном слове стоит на позиции 30. Отсюда и «огромное» значение: для `float` это скромная двойка, а для `int` — четверть диапазона.

Поведение на разных уровнях оптимизации:

| | `alias(&i, (float*)&i)` | Почему |
|---|---|---|
| `-O0` | **1073741824** | компилятор честно перечитывает память, а там уже лежат биты `2.0f` |
| `-O2` | **1** | strict aliasing: `int*` и `float*` не могут указывать на одну память, значит `*f = 2.0f` не мог задеть `*i`, и `return *i` сворачивается в записанную ранее единицу |

Оба ответа «правильные», потому что программа нарушает strict aliasing и её поведение не определено. Это и есть UB: разные уровни оптимизации дают разные результаты, и ни один из них не является ошибкой компилятора.

### Откуда именно берётся 1: ассемблер

```asm
; gcc -O0                              ; gcc -O2 — функция целиком
        movq    -8(%rbp), %rax                 movl    $1, (%rdi)          ; *i = 1
        movl    $1, (%rax)          ; *i = 1   movl    $1, %eax            ; возврат = 1, БЕЗ чтения памяти
        movq    -16(%rbp), %rax                movl    $0x40000000, (%rsi) ; *f = 2.0f
        movss   .LC0(%rip), %xmm0              ret
        movss   %xmm0, (%rax)       ; *f = 2.0f
        movq    -8(%rbp), %rax
        movl    (%rax), %eax        ; ПЕРЕЧИТЫВАЕМ память  <-- этой инструкции на -O2 нет
        ret
```

На `-O0` инструкция `movl (%rax), %eax` действительно лезет в память, а там уже лежат биты `2.0f`, отсюда 1073741824.

На `-O2` чтения из памяти **нет вообще**. Компилятор применил store-to-load forwarding: «в `(%rdi)` только что записана единица, а запись по `(%rsi)` — это `float`, она по правилу strict aliasing не может задеть объект типа `int`, значит перечитывать незачем». Результат `1` подставлен константой.

Обратите внимание на порядок инструкций: `movl $1, %eax` стоит **раньше**, чем запись `0x40000000`. Возвращаемое значение готово ещё до того, как в память попадёт `2.0f`.

Отсюда самое наглядное следствие:

```
gcc -O0:  функция вернула 1073741824, в памяти лежит 1073741824    (согласовано)
gcc -O2:  функция вернула 1,          в памяти лежит 1073741824    <-- РАЗНЫЕ числа
```

На `-O2` функция вернула значение, которого в читаемой ею переменной никогда не было. Память при этом записана корректно, обе записи на месте. Расходится именно результат `return *i`.

Корректный способ посмотреть на биты числа — `memcpy` (в примере он и используется для получения эталонного значения) либо `union` в C. Оба варианта компилятор распознаёт и не порождает лишнего копирования.

## 2c. Почему `volatile` не чинит strict aliasing

`09_volatile_aliasing.c`. Разбор попытки поставить `volatile float *f`.

Результаты `gcc -O2` (1 = чтение свёрнуто, 1073741824 = память перечитана):

| Вариант | `-O0` | `-O2` | `-O2 -fno-strict-aliasing` |
|---|---|---|---|
| A) без `volatile` | 1073741824 | **1** | 1073741824 |
| B) `volatile float *f` — на ЗАПИСИ | 1073741824 | **1** | 1073741824 |
| C) `volatile int *i` — на ЧТЕНИИ | 1073741824 | **1** | 1073741824 |
| D) `volatile` на обеих | 1073741824 | 1073741824 | 1073741824 |
| E) `__attribute__((may_alias))` | 1073741824 | 1073741824 | 1073741824 |
| F) `memcpy` (без UB) | 1073741824 | 1073741824 | 1073741824 |

### B) `volatile` на записи не помогает

```asm
b_vol_write:
        movl    $1, (%rdi)          ; *i = 1
        movl    $1, %eax            ; возврат = 1 — чтение всё равно свёрнуто
        movss   %xmm0, (%rsi)       ; *f = 2.0f — запись выполнена, volatile её сохранил
```

`volatile` сделал ровно то, что обещает: запись через `f` не выброшена. Но `volatile` — свойство **пути доступа**, а не участка памяти. Он ограничивает обращения через `f` и **ничего не говорит про `i`**. Чтение `*i` остаётся обычным, и компилятор по-прежнему считает, что запись типа `float` не могла задеть объект типа `int`. Значение подставляется напрямую.

Кроме того, `volatile float` — это всё ещё тип `float`. Квалификатор не меняет правило алиасинга: обращаться к объекту типа `int` через lvalue типа `float` нельзя ни с `volatile`, ни без него.

### C) `volatile` на чтении тоже не помогает — и это самое интересное

```asm
c_vol_read:
        movl    $1, (%rdi)            ; *i = 1
        movl    (%rdi), %eax          ; чтение ЕСТЬ — volatile заставил его выполнить
        movl    $0x40000000, (%rsi)   ; *f = 2.0f — записано ПОСЛЕ чтения!
```

`volatile` своё дело сделал: загрузка из памяти появилась, её не свернули. Но компилятор **переставил** запись `*f = 2.0f` за эту загрузку. Он вправе так поступить: `volatile` упорядочивает volatile-обращения только относительно **других volatile-обращений**. Обычный доступ можно перемещать через volatile-доступ, тем более что по strict aliasing они всё равно «не пересекаются».

В итоге чтение видит записанную единицу, а `2.0f` попадает в память уже потом.

### D) `volatile` на обеих сторонах меняет результат, но не делает программу корректной

```asm
d_vol_both:
        movl    $1, (%rdi)
        movss   %xmm0, (%rsi)         ; теперь оба доступа volatile
        movl    (%rdi), %eax          ; и переставлять их нельзя
```

Оба обращения volatile, порядок программы обязан сохраниться, чтение видит биты `2.0f`. Но это **не исправление**: программа по-прежнему нарушает strict aliasing и остаётся с неопределённым поведением. Мы просто связали оптимизатору руки настолько, что он случайно выдал ожидаемое. Другая версия компилятора, другой уровень оптимизации или другая архитектура вправе дать иной результат.

### Что действительно решает задачу

| Способ | Что это | Корректно? |
|---|---|---|
| `memcpy` | компилятор распознаёт и не порождает лишних копий | **да**, полностью по стандарту |
| `union` (в C) | чтение не через записанный член разрешено в C | **да** в C; в C++ формально UB |
| приведение к `char*`/`unsigned char*` | символьные типы вправе алиасить всё | **да** |
| `__attribute__((may_alias))` | расширение gcc/clang: тип может алиасить любой | да, но непереносимо |
| `-fno-strict-aliasing` | отключает правило для всей сборки | да, но платим скоростью (см. раздел 3: 1.16 с против 3.30 с) |
| `volatile` | **не средство для этого** | **нет** |

### Диагностика

- `-Wstrict-aliasing` (в составе `-Wall` при `-O2`) предупреждение выдаёт: `dereferencing type-punned pointer might break strict-aliasing rules`. Оно эвристическое и ловит не все случаи.
- **UBSan нарушение strict aliasing не ловит вообще**: проверено, 0 сообщений. Это статическое правило типов, а не проверяемое во время выполнения условие. Отсюда правило: полагаться только на санитайзеры здесь нельзя, нужны предупреждения компилятора и дисциплина при приведении указателей.

## 2d. Как получить type punning на `-O2`

`10_punning_right.c`. Вопрос: если нельзя `*(uint32_t*)&f`, то как всё-таки посмотреть на те же байты как на другой тип и получить это на `-O2`?

Четыре законных способа, все дают `1073741824` на `-O0` и на `-O2`:

```c
// 1. memcpy — канонический способ, полностью по стандарту
uint32_t via_memcpy(float f){ uint32_t u; memcpy(&u, &f, sizeof u); return u; }

// 2. union — разрешено в C (чтение не через записанный член); в C++ формально UB
uint32_t via_union(float f){ union { float f; uint32_t u; } p; p.f = f; return p.u; }

// 3. char* — символьные типы вправе алиасить любой объект
uint32_t via_char(float f){ uint32_t u; unsigned char *d=(unsigned char*)&u, *s=(unsigned char*)&f;
                            for (size_t k=0;k<sizeof u;k++) d[k]=s[k]; return u; }

// 4. may_alias — расширение gcc/clang, непереносимо
typedef uint32_t __attribute__((may_alias)) u32_ma;
uint32_t via_may_alias(float f){ return *(u32_ma*)&f; }
```

В C++20 к этому добавляется `std::bit_cast<uint32_t>(f)` — то же самое, но выражением и с проверками на этапе компиляции.

### Корректность бесплатна

Главный аргумент: на `-O2` все четыре варианта компилируются **в одну и ту же единственную инструкцию** — ровно ту же, что и UB-версия:

```
via_memcpy    :  movd %xmm0, %eax ; ret
via_union     :  movd %xmm0, %eax ; ret
via_char      :  movd %xmm0, %eax ; ret
via_may_alias :  movd %xmm0, %eax ; ret
via_cast_UB   :  movd %xmm0, %eax ; ret      <- UB-вариант, ровно то же самое
```

Ни вызова `memcpy`, ни цикла по байтам, ни обращения к стеку. Бенчмарк тут бессмысленен: машинный код побайтово совпадает. За отказ от UB не платят ничего.

### Компилятор оптимизирует лучше, когда ему не врут

Исходный сценарий (записать `int`, затем `float` в ту же память, прочитать как `int`), переписанный на `memcpy`:

```c
int rmw_memcpy(void *p){
    int one = 1;    memcpy(p, &one, 4);
    float two=2.0f; memcpy(p, &two, 4);
    int r;          memcpy(&r, p, 4);
    return r;
}
```
```asm
rmw_memcpy:
        movl    $1073741824, (%rdi)   ; первая запись мертва и выброшена
        movl    $1073741824, %eax     ; ответ посчитан на этапе компиляции
        ret
```

Компилятор увидел все три `memcpy` насквозь, понял, что запись единицы затирается, убрал её и свернул результат в константу. Две инструкции, ни одного вызова. При этом ответ **правильный**, в отличие от `-O2`-версии с нарушением алиасинга, где получалась единица.

Это и есть содержательный вывод: UB не «разрешает оптимизацию, которая иначе невозможна». Когда компилятор получает достоверную информацию об алиасинге, он оптимизирует агрессивнее и при этом корректно.

### Если переписывать нечего

Когда кода много и переписать его нельзя, остаётся `-fno-strict-aliasing` на всю единицу трансляции. Так собирается ядро Linux. Цена измерена в разделе 3: 1.16 с против 3.30 с, примерно втрое. Это выключение правила для всего файла, поэтому точечный `memcpy` почти всегда выгоднее.

## 2e. Что именно исчезает: запись `*f = 2.0f` или чтение `*i`?

`11_which_one_dies.c`. Разбор гипотезы «запись `*f = 2.0f` выкидывается как не имеющая дальнейшего эффекта».

**Гипотеза неверна. Запись остаётся, исчезает чтение.**

Прямая проверка: смотрим и возвращаемое значение, и то, что реально лежит в памяти после вызова.

```
gcc -O0:  функция вернула 1073741824, в памяти 1073741824  (байты 00 00 00 40)
gcc -O2:  функция вернула 1,          в памяти 1073741824  (байты 00 00 00 40)
```

На `-O2` в памяти лежат биты `2.0f`. Значит запись `*f = 2.0f` **выполнилась** и никуда не делась. А вернулась единица, которой в этой памяти никогда не было, — значит пропало именно чтение.

Ассемблер показывает судьбу всех трёх операций:

```asm
alias:
        movl    $1, (%rdi)            ; запись A (*i = 1)      — НА МЕСТЕ
        movl    $1, %eax              ; чтение C (return *i)   — ЗАМЕНЕНО КОНСТАНТОЙ
        movl    $0x40000000, (%rsi)   ; запись B (*f = 2.0f)   — НА МЕСТЕ
        ret
```

Обе записи присутствуют. Исчезла только загрузка из памяти.

### Почему записи нельзя выбросить

`i` и `f` указывают на память **вызывающего кода**. Обе записи — наблюдаемый снаружи побочный эффект, и компилятор обязан их сохранить. Запись можно удалить лишь тогда, когда доказано, что её кто-то затирает, либо что объект мёртв (например, локальная переменная, адрес которой никуда не утёк).

Здесь и возникает ирония: компилятор считает, что `int*` и `float*` указывают на **разные** объекты. Раз разные — значит запись B не затирает запись A, и **ни одну из них удалить нельзя**. То самое предположение, которое убивает чтение, одновременно не даёт тронуть записи.

### Механизм называется store-to-load forwarding

Компилятор рассуждает так:
1. «В `(%rdi)` я только что записал единицу.»
2. «Дальше есть запись в `(%rsi)`, но её тип `float`, а читаю я `int`. По strict aliasing они не могут указывать на один объект, значит содержимое `(%rdi)` не изменилось.»
3. «Тогда перечитывать память незачем — подставлю записанное значение.»

Шаг 2 и есть ложная посылка: в нашей программе `%rdi` и `%rsi` — один и тот же адрес. Но правило языка разрешает компилятору так считать, поэтому ошибка целиком на стороне программы.

Обратите внимание на порядок инструкций: `movl $1, %eax` стоит **раньше** записи `0x40000000`. Возвращаемое значение готово ещё до того, как `2.0f` попадёт в память. Это тоже следствие предположения о независимости: раз обращения не пересекаются, их можно переставлять.

## 2f. Чем UB отличается от implementation-defined

Разбор возражения: «любой код всё равно во что-то компилируется и что-то конкретное делает, значит и UB по сути implementation-defined».

Интуиция понятна, но она исходит из модели «компилятор — переводчик, который отображает каждую конструкцию исходника в фиксированный машинный код». Компилятор так не работает: он **рассуждает о программе** и использует UB как **логическую посылку**. Отсюда три различия, которые видны в опытах.

### Различие 1: implementation-defined обязан быть один и задокументирован

| | Implementation-defined | Undefined |
|---|---|---|
| Сколько вариантов поведения | конечный набор из стандарта, реализация выбирает **один** | требований нет вообще |
| Обязанность документировать | **да**, это требование стандарта | нет |
| Одинаково ли в разных местах программы | **да** | **не обязано** |
| Корректна ли программа | **да**, просто непереносима | **нет**, она некорректна целиком |
| Можно ли полагаться | да, на конкретной реализации | нет, никогда |

### Различие 2: одно выражение — разные ответы в одном бинарнике

`12_ub_vs_impdef.c` ставит их рядом.

```
=== implementation-defined: (-8) >> 1 ===
  константа в исходнике : -4
  через noinline-функцию: -4
  встроенная версия     : -4
  все три совпали, и gcc это ДОКУМЕНТИРУЕТ (арифметический сдвиг)

=== UB: (INT_MAX + 1) > INT_MAX ===
  константа в исходнике : 0
  через noinline-функцию: 1
  встроенная версия     : 1
  одно и то же выражение, один бинарник, РАЗНЫЕ ответы
```

Это и есть граница. Для `>>` реализация обязана выбрать один вариант и его описать: gcc документирует арифметический сдвиг, и он одинаков везде, на всех уровнях оптимизации. Для знакового переполнения никакого «выбора реализации» не существует: при свёртке константы gcc заворачивает значение и даёт 0, а во время выполнения исходит из того, что переполнения не бывает, и даёт 1. Одно выражение, один компилятор, один запуск — два ответа. Implementation-defined так себя вести не может по определению.

### Различие 3: UB стирает код, а не подставляет значение

`13_ub_not_a_value.c` — самый показательный случай.

```c
int f(int x){ int r; if (x > 0) r = 10; return r; }   // при x<=0 чтение r — UB
int g(int x){ int r = 0; if (x > 0) r = 10; return r; }  // то же самое, но без UB
```
```
вход x = -5  (ветка if выполниться НЕ должна)

gcc -O0:   f(-5) = 0    g(-5) = 0
gcc -O2:   f(-5) = 10   g(-5) = 0
```

Ассемблер объясняет, откуда взялась десятка:

```asm
; f — с UB, вся функция          ; g — без UB
f:      movl    $10, %eax        g:      testl   %edi, %edi
        ret                              movl    $0, %edx
                                         movl    $10, %eax
                                         cmovle  %edx, %eax
                                         ret
```

В `f` **нет ни проверки `x > 0`, ни второго исхода**. Рассуждение компилятора: «если `x <= 0`, программа читает неинициализированную переменную, то есть совершает UB; UB не бывает; значит `x > 0` истинно всегда; значит `r` всегда 10». Условие исчезло не как «оптимизация вычисления», а как вывод из посылки.

Обратите внимание: `f(-5)` вернула 10, хотя присваивание `r = 10` находится внутри ветки, которая при `x = -5` заведомо не выполняется. Это не «мусор со стека» и не «что решило железо» — на `-O0` там как раз был ноль со стека. Никакая реализация арифметики или регистров такого дать не может, потому что результат порождён **логикой оптимизатора, а не машиной**.

### Почему «всё равно же что-то выполнится» не спасает

Верно, что готовый бинарник делает нечто конкретное и детерминированное. Неверен следующий шаг: что это «нечто» — свойство реализации, на которое можно опереться. Разница в том, **где именно зафиксирован выбор**:

- **Implementation-defined**: выбор сделан **заранее и на уровне языка**. `sizeof(long) == 8` в этом ABI — контракт. Он одинаков для любой программы, описан в документации, и по нему можно программировать.
- **UB**: никакого выбора нет. Есть результат работы оптимизатора над конкретным фрагментом, зависящий от соседнего кода, от того, встроилась ли функция, от уровня оптимизации, от версии компилятора и от флагов. Тот же исходник в другом месте той же программы даст другое (различие 2). Добавление `printf` рядом может поменять результат.

Ещё три свойства UB, которых у implementation-defined не бывает:

1. **Последствия не локальны.** Удаляется не только «плохая» операция, но и код вокруг: проверка на `NULL` (раздел 2a), проверка переполнения (раздел 2a), целая ветка `if` (здесь).
2. **Последствия могут идти назад по тексту.** Компилятор вправе перенести или удалить код, стоящий **до** места с UB, раз этот путь всё равно объявлен невозможным.
3. **`-fwrapv` превращает UB в определённое поведение.** Это доказывает, что дело не в железе: инструкция `add` на x86 всегда заворачивала значение. UB — свойство **языка и модели оптимизатора**, а не процессора. Выбрать поведение может флаг компилятора, но по умолчанию стандарт его не задаёт.

### Короткий ответ

Implementation-defined — это «стандарт разрешил несколько вариантов, **реализация обязана выбрать один, описать его и придерживаться**; программа корректна». UB — это «**никаких требований к программе целиком**; компилятор вправе считать, что этого не происходит, и делать выводы, стирающие произвольный код». Первое — точка расширения языка, второе — отсутствие языка в этой точке.

### Оговорка по опытам

Знаменитый пример с вызовом функции через неинициализированный указатель (когда программа вызывает функцию, которую никто не вызывал) **на gcc 14 воспроизвести не удалось**: компилятор честно сгенерировал `call *fp(%rip)`, и программа упала с SIGSEGV на обоих уровнях оптимизации. Это поведение clang; clang в этом окружении отсутствует, проверить не на чем. Пример с неинициализированной переменной выше воспроизводится на gcc 14 стабильно и показывает то же самое.

## 2g. Как эти виды поведения определяются и что такое defined behaviour

### Где это записано

Все определения — в разделе 3.4 стандарта C (нумерация по C17, в C23 та же):

- **3.4 behavior** — «внешнее проявление или действие» (*external appearance or action*).
- **3.4.1 implementation-defined behavior** — «**unspecified behavior**, где каждая реализация документирует, как делается выбор».
- **3.4.3 undefined behavior** — «поведение при использовании непереносимой или ошибочной конструкции программы либо ошибочных данных, **к которому настоящий стандарт не предъявляет никаких требований**».
- **3.4.4 unspecified behavior** — «использование неуточнённого значения или иное поведение, для которого стандарт предоставляет **два или более варианта** и не накладывает дальнейших требований на то, какой выбран в каждом конкретном случае».

Отсюда сразу структурный факт, который обычно упускают: **implementation-defined — это частный случай unspecified**. Разница ровно одна — обязанность документировать выбор.

```
                  поведение, полностью заданное стандартом   <- "defined"
                                    |
                  стандарт даёт НЕСКОЛЬКО вариантов
                         /                        \
                  unspecified              implementation-defined
              (документировать        (обязана выбрать один
               не обязана)             и ЗАДОКУМЕНТИРОВАТЬ)

                  стандарт не предъявляет требований вообще
                                    |
                            undefined behavior
```

### Откуда берётся UB: по умолчанию, в том числе молчанием

Ключевой абзац — §4 p2 (Conformance):

> Если нарушено требование «shall» или «shall not», стоящее вне constraint, поведение не определено. Undefined behavior обозначается в стандарте словами «undefined behavior» **либо опущением любого явного определения поведения**.

То есть UB возникает тремя путями:

1. Стандарт прямо пишет «the behavior is undefined» (около 200 мест в C17).
2. Нарушено требование `shall`, стоящее вне раздела Constraints.
3. **Стандарт просто молчит.** Это и есть ответ на вопрос «разве не всякое UB — implementation-defined?». Умолчание стандарта означает не «пусть решает реализация», а именно UB. Молчание — это не делегирование выбора, это отсутствие требований.

Отдельно стоит **constraint violation**. Нарушение ограничения из раздела Constraints требует **обязательной диагностики**, и это не UB. Именно поэтому `printf(42)` из строки 15 в `01_behaviors.c` компилятор отверг с ошибкой (`passing argument 1 makes pointer from integer without a cast`), причём даже под `-w`: это нарушение ограничения, а не UB. UB, напротив, диагностировать никто не обязан, и обычно никто не может.

### Что такое defined behaviour

Прямого термина «defined behavior» в стандарте **нет**. Это разговорное название для «всего остального»: поведения, которое стандарт задаёт однозначно. Механизм, которым он это делает, описан в §5.1.2.3 и состоит из трёх частей.

**1. Абстрактная машина.** Стандарт описывает не x86 и не ARM, а идеализированную машину, выполняющую программу строго по тексту, шаг за шагом. Смысл конструкций языка определён в её терминах.

**2. Наблюдаемое поведение** (*observable behavior*). Из всего, что делает абстрактная машина, наблюдаемым объявлено только:
- обращения к объектам, объявленным `volatile`, строго в порядке текста программы;
- ввод-вывод: данные, записанные в файлы, должны совпадать с тем, что предписывает абстрактная машина;
- содержимое интерактивных устройств к моменту ожидания ввода.

**3. Правило as-if** (§5.1.2.3 p6). Реализация обязана воспроизвести **только наблюдаемое поведение** абстрактной машины. Всё остальное она вправе делать как угодно: переставлять, удалять, вычислять заранее, векторизовать.

Это и есть источник всех оптимизаций, разобранных выше. `14_abstract_machine.c` показывает правило в чистом виде:

```c
void not_observable(void){ int sum=0; for(int i=0;i<1000000;i++) sum += i*i; (void)sum; }
void observable(void)    { volatile int sink=0; for(int i=0;i<1000000;i++) sink = i*i; }
```
```
200 x миллион итераций:
  без наблюдаемых эффектов : 0.0000 с
  с volatile (наблюдаемо)  : 0.0559 с
```
```asm
not_observable:
        endbr64
        ret               ; миллиона итераций просто нет
```

Цикл без наблюдаемых эффектов удалён целиком — программа обязана совпадать с абстрактной машиной только по наблюдаемому, а наблюдать тут нечего. Стоит объявить приёмник `volatile`, и тот же цикл обязан выполниться полностью.

Это же объясняет раздел 2c: `volatile` — не средство против алиасинга, а единственный способ сказать «данное обращение наблюдаемо, трогать его нельзя».

Оговорка по опыту: функцию `same_result` (сумма от 0 до n) правило as-if позволяет заменить формулой `n(n+1)/2`, но **gcc 14 этого не сделал** и цикл оставил. Правило разрешает оптимизацию, а не обязывает к ней.

### Сводка: как отвечать на вопрос «какое здесь поведение»

| Что сказано в стандарте | Вид | Обязанности реализации | Корректна ли программа |
|---|---|---|---|
| один требуемый результат | defined | воспроизвести наблюдаемое поведение | да |
| несколько вариантов, выбрать и описать | implementation-defined | выбрать, **задокументировать**, соблюдать | да |
| несколько вариантов, описывать не нужно | unspecified | выбрать любой, можно каждый раз разный | да |
| «behavior is undefined», нарушен `shall`, либо **молчание** | undefined | никаких | **нет** |
| нарушен constraint | — | **выдать диагностику** | нет, но ошибку обязаны показать |

Практический вывод к исходному вопросу: реализация действительно всегда делает что-то конкретное — но при implementation-defined это **обязательство, на которое можно опереться**, а при UB это лишь побочный результат работы оптимизатора над конкретным фрагментом кода. Разделы 2e и 2f показывают, во что он превращается: исчезнувшее чтение, стёртая ветка `if`, два разных ответа для одного выражения в одном бинарнике.

## 4. Чем UB полезно системному программисту

1. **Скорость**: компилятор не вставляет проверки, держит значения в регистрах (aliasing), считает число итераций и векторизует циклы (знаковый счётчик не переполняется).
2. **Переносимость без цены**: стандарт не навязывает единую семантику архитектурам (x86, ARM, DSP), и код эффективно ложится на каждую.
3. **Диагностика**: раз поведение не определено, санитайзеры (UBSan, ASan) и `-ftrapv` вправе его ловить, не нарушая стандарт.
4. **Расширения реализации**: `-fwrapv` (так собирается ядро Linux), `-fno-strict-aliasing`, `__builtin_*_overflow` дают определённое поведение там, где оно нужно.

## 5. Практика

- Отладка под `-fsanitize=undefined,address`.
- Type punning через `memcpy` (или `union` в C), а не приведением указателей.
- Знаковое переполнение проверять до операции: `__builtin_add_overflow`.
- Нужно оборачивание, используйте `unsigned`.
- «У меня работает» не доказывает отсутствие UB: результат зависит от версии компилятора и флагов оптимизации.
